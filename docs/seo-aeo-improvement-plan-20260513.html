SEO / AEO Improvement Plan

村山良作搜尋與 AI 引用能見度改善計畫

本報告依據 2026-05-13 本地程式碼盤點、既有文件、Google Search Central、OpenAI 與 Perplexity crawler 文件，提出 90 天改善方案。重點不是堆關鍵字，而是讓搜尋引擎與 AI 回答引擎都能穩定理解「村山良作是誰、服務什麼、有哪些可信案例」。

一、執行摘要

SEO 現況推估 7.4 / 10

首頁、合作流程、囍茶、MUSE 與作品 SSR 已有 metadata、canonical、OG/Twitter 與部分 schema；缺口集中在支援頁 metadata、私有頁 noindex、內容集群與 Search Console 驗證。

AEO/GEO 現況推估 6.2 / 10

已具備 llms.txt、LocalBusiness、Service、FAQPage、CreativeWork 基礎，但尚未建立 ChatGPT、Claude、Gemini、Perplexity 的引用基準，無法量化 AI 可見度。

90 天目標 8.5+

讓所有可索引頁有明確主題、可驗證結構化資料、可爬取文字內容與明確內鏈；建立 AI citation baseline，並用同一組 prompts 追蹤改善。

主要策略

先修技術風險，再建立服務主題集群，最後針對 AI 回答常見提問補齊「可被引用的答案型內容」。SEO 與 AEO 是互補關係：SEO 先確保索引與可信度，AEO 再透過清楚的實體、FAQ、比較表、案例方法論與第三方訊號提高被引用機率。

二、現況發現

項目 目前狀態 風險 建議
首頁基礎 SEO 已有 title、description、canonical、OG/Twitter、LocalBusiness、Service、FAQPage。 首頁 description 偏短，首頁作品卡由 JS/API 渲染，非 Google 類 crawler 可能較難完整讀到作品列表。 補一段可見文字型服務摘要與精選案例內鏈；首頁 description 可擴充到 70-110 中文字。
動態作品頁 /works/{id} server.py 會產生 SSR 頁面，含 title、description、canonical、OG/Twitter、CreativeWork schema。 本地舊資料有 29 件作品；README 顯示正式環境改用 PostgreSQL，需確認正式 sitemap 是否吃到正式資料源。 上線環境抽查 10 個作品 URL：HTTP 200、canonical 正確、GSC 可檢索、schema 無錯。
Sitemap 靜態 sitemap.xml 只列 4 個 URL；server.py 動態路由會列靜態頁與作品頁。 若部署或 CDN 直接服務靜態檔，作品頁可能不在 sitemap；若走 Python server，需確認 Cloudflare 沒快取舊檔。 以正式站 curl https://goodjob.weddingwishlove.com/sitemap.xml 驗證；提交到 Google Search Console。
Robots / 私有頁 robots.txt 封鎖 /quote/，且 server 對 quote 頁送 X-Robots-Tag。 /admin/ 未在 robots 或 response header 明確 noindex；後台頁 title 為 CMS，可能被發現。 對 /admin/ 加 X-Robots-Tag: noindex, nofollow，並在 robots disallow。
支援銷售頁 sort-hat/ 有 description 但無 canonical；wedding-packages/* 有 title 但缺 description/canonical/schema。 這些頁面有商業搜尋價值，但目前搜尋摘要與索引訊號不足。 補齊 canonical、OG/Twitter、Product/Service/FAQ/Breadcrumb schema，並納入內容集群。
AEO 基礎 已有 llms.txt，內容摘要清楚；首頁與流程頁有 FAQ。 沒有跨平台 citation baseline；無法知道 ChatGPT、Claude、Gemini、Perplexity 目前是否推薦競品。 先做 20-40 題 prompt 實測，再依 lost prompts 建立 FAQ、比較、選購指南、案例頁。

三、優先級改善計畫

P07 天內：索引安全與技術基礎校正

  • 確認正式站 /sitemap.xml 是否包含 PostgreSQL 中所有正式作品頁，並排除舊靜態 sitemap 被 CDN 快取的可能。
  • 為 /admin/ 加入 X-Robots-Tag: noindex, nofollow, noarchive，robots 同步 disallow。
  • 補齊 sort-hat/、wedding-packages/、wedding-packages/outdoor.html 的 description、canonical、OG/Twitter 與 schema。
  • 用 Google Rich Results Test 驗證首頁、流程頁、MUSE 頁與 5 個作品頁的 JSON-LD，確認 schema 內容與頁面可見文字一致。
  • 在首頁加入伺服器或靜態 HTML 可讀的精選案例摘要與服務內鏈，降低純 JS 渲染對 AI crawler 的不確定性。

P130 天內：服務主題集群與內容 ownership

  • 從 Search Console 匯出最近 3 個月 page + query 資料，先做 cannibalization audit，再決定 title/H1/內容調整。
  • 建立 5 個 pillar 頁：品牌活動佈置、展場空間設計、春酒尾牙佈置、戶政空間改造、婚禮場景佈置。
  • 將 29+ 件作品頁歸到對應 cluster，作品頁加回連到 pillar 頁，pillar 頁連到代表作品與 FAQ。
  • 作品頁模板擴充為案例格式：活動背景、場地限制、設計策略、製作亮點、適合產業、成果照片。
  • 每個服務 cluster 建立 4-6 題實務 FAQ，答案以 60-120 字直接回答，方便 AI 摘錄。

P260 天內：AEO / GEO 引用率提升

  • 建立跨平台 citation baseline：ChatGPT、Claude、Gemini、Perplexity 各測 20-40 題，記錄品牌是否被提及、是否被引用、競品是誰。
  • 針對 lost prompts 製作答案型內容：活動佈置公司怎麼選、品牌活動佈置預算、展場設計與拍照牆差異、春酒尾牙主題提案。
  • 新增比較表與決策框架，讓 AI 有可摘錄的 criteria，例如預算區間、施工時間、撤場、場地尺寸、互動需求。
  • 更新 llms.txt：加入服務分類、代表作品 URL、獎項頁、聯絡方式與最近更新日期；每月檢查一次。
  • 確認 robots / WAF 允許 OAI-SearchBot、PerplexityBot 與一般搜尋 crawler 讀取公開內容。

P390 天內：權威訊號與持續成長

  • 建立「得獎與媒體」頁，集中 MUSE、合作策展、第三方報導與高可信外部連結。
  • 推動可被引用的外部訊號：合作單位頁面、媒體稿、案例採訪、Google Business Profile、社群固定貼文。
  • 每月發布 2 篇長尾內容，聚焦真實業主問題，不做泛用靈感文。
  • 建立 Looker Studio 或表格週報，追蹤 GSC、GA4、AI referral、表單/LINE 點擊。

作品頁模板建議

必備區塊

  • 一句話摘要：這是什麼活動、服務對象、場地類型。
  • 需求與限制：預算、時間、場地、品牌規範、動線。
  • 解法：主視覺、材質、花藝、施工、互動。
  • 結果：照片、社群擴散、現場體驗、得獎或客戶回饋。

Schema 建議

  • CreativeWork 或 Article：案例內容。
  • ImageObject：重要圖片與 caption。
  • BreadcrumbList：首頁 > 服務 > 案例。
  • FAQPage：該類案例常見問題。

五、AEO / GEO 引用策略

AI 回答引擎的重點是「能不能把品牌放進答案裡，並把站內或第三方頁面當成可信來源」。這無法保證，只能提高引用機率，所以第一步必須建立基準測量。

Baseline prompt 組

意圖 測試 prompt 範例 期望內容資產
推薦 「台灣有哪些適合品牌發表會的活動佈置公司？」 品牌活動 pillar、代表案例、公司介紹、第三方提及。
比較 「品牌活動佈置和展場設計公司要怎麼選？」 比較表、選擇框架、服務邊界說明。
預算 「企業尾牙拍照區和舞台佈置通常要準備哪些資訊？」 流程頁 FAQ、需求清單、預算影響因子。
案例 「有沒有沉浸式昆蟲展或花藝展場設計案例？」 MUSE 得獎頁、成美文化園案例頁、圖片 caption。
地方/公部門 「戶政事務所打卡牆或公共空間改造有哪些做法？」 戶政 cluster、各區案例、設計方法論。

AI 引用修補包

修補包 內容 預期影響
Entity clarity 統一品牌名「村山良作 MURAYAMA GOODJOB」、母品牌「村花弄囍」、服務範圍、所在地、sameAs。 讓 AI 與搜尋引擎穩定識別品牌實體。
Prompt-matched FAQ 把「怎麼選、多少錢、要準備什麼、多久前洽詢、適合哪些活動」做成短答案。 提高 FAQ 型、how-to 型問題被摘錄機率。
Comparison pages 建立「品牌活動佈置 vs 展場設計」、「客製佈置 vs 套組方案」等中立比較頁。 回應 AI 常見比較型 prompt。
Third-party proof 整理 MUSE 得獎、合作單位、媒體報導、社群案例，並取得外部頁面連回。 增加可信來源與非自家內容佐證。

六、衡量方式與 90 天時程

第 1-2 週

技術修補、正式 sitemap 驗證、admin noindex、支援頁 metadata/schema、GSC URL Inspection。

第 3-4 週

GSC query/page 匯出、cannibalization map、服務 pillar 架構、內鏈規劃。

第 5-8 週

上線 pillar 頁、改作品案例模板、補 FAQ/比較表、更新 llms.txt。

第 9-12 週

AI citation recheck、競品 gap 分析、外部權威訊號、月報與下一輪內容排程。

KPI

面向 指標 90 天目標
Indexation 有效索引頁數、sitemap 收錄率、URL Inspection 狀態。 公開頁 90%+ 可索引；私有頁 0 筆索引。
Organic 非品牌 impressions/clicks、前 10 名關鍵字數、CTR。 建立 baseline 後每月成長；先看 impressions，再看 clicks。
Technical LCP、INP、CLS、HTTP 200、schema validation。 Core Web Vitals 達 Good；主要 schema 無錯誤。
AEO/GEO 跨平台 citation rate、lost prompts、競品 share of voice、AI referral。 第 1 次只建 baseline；第 2 次追蹤引用率與品牌提及率提升。
Conversion LINE 點擊、詢問表單、電話/社群點擊、作品頁停留。 把搜尋與 AI 流量連到可追蹤的詢問動作。

必要資料缺口

  • Google Search Console 最近 3-6 個月 query/page 資料。
  • GA4 或伺服器 log：自然搜尋、ChatGPT/Perplexity referral、LINE CTA 點擊。
  • 正式 PostgreSQL 作品數與正式 sitemap 實際輸出。
  • 4 個 AI 平台同一組 prompts 的 citation baseline。

七、參考依據

  • Google Search Central：AI features and your website。重點：AI Overviews / AI Mode 仍以 SEO fundamentals、可索引、可讀文字、內鏈、page experience、structured data 與可見文字一致為基礎。
  • Google Search Technical Requirements。重點：公開可存取、Googlebot 不被封鎖、HTTP 200、具可索引內容。
  • Google Structured Data Markup Supported Features。重點：Organization、LocalBusiness、FAQ、Breadcrumb、Article、Image metadata 等可支援 rich result 或理解頁面內容。
  • OpenAI Publishers and Developers FAQ。重點：公開網站可出現在 ChatGPT search，需避免封鎖 OAI-SearchBot，可用 analytics 追蹤 utm_source=chatgpt.com referral。
  • Perplexity Crawlers。重點：PerplexityBot 用於搜尋結果索引與連結，若有 WAF/CDN 需明確允許 bot 與官方 IP。
