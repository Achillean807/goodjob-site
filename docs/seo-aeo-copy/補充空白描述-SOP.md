# 相簿空白描述補文案 SOP

本文件定義「補充空白描述」類任務的標準流程。之後只要使用者提到「補充空白描述」、「補空白文案」、「補相簿敘述」、「沒有描述的相簿」、「description 空白」、「補 SEO/AEO 介紹文案」等近似用詞，就依本文件處理。

## 任務目標

為正式站目前 `description` 為空的作品相簿，根據標題、分類與照片撰寫可上線的繁體中文介紹文案。文案需兼顧 SEO、AEO、品牌語氣與 B2B CTA，並先產出 review 檔給人工確認，不直接覆蓋正式資料。

## 參考風格

主要參考 `docs/seo-aeo-copy/album-descriptions-20260505.json` 裡的 `newDescription`。這批文案比舊文更適合正式站，特徵如下：

- 第一句用現場畫面破題，例如「燈光一亮」、「賓客走到拍照區前」、「百貨人潮快速經過」。
- 不先喊服務口號，而是先讓讀者看見活動情境。
- 第二段才寫村山良作的設計方法：入口、主舞台、拍照牆、花藝、道具、動線、攝影角度、品牌識別。
- 句子要有畫面，但避免過度華麗或空泛，例如「極致」、「完美」、「震撼全場」要少用或不用。
- 每篇都要自然帶入適用場景，例如企業尾牙、春酒、品牌活動、快閃活動、展區佈置、婚禮佈置、戶政拍照牆。
- 結尾要把「好看」轉成商業價值：願意拍照、願意分享、留下記憶點、增加品牌辨識度、讓活動素材可延伸使用。

`docs/seo-aeo-copy/new-albums-20260506.md` 可作為流程與欄位參考，但文案語氣以 20260505 版本為主。20260506 的長文案若偏硬廣，需再收斂成較自然的正式站語氣。

## 資料來源原則

正式資料源是 PostgreSQL `goodjob_site`，不是本機 `data/articles.json`。補文案時可用正式站 API 抓取快照做草稿，但最後是否寫回資料庫必須由使用者確認。

預設處理順序：

1. 抓取正式站文章資料。
2. 篩出 `description` 為空或只有空白字元的作品。
3. 取得每篇標題、分類、封面圖、圖片 URL 與現有排序。
4. 建立可回溯的 snapshot 與 review 檔。
5. 使用 Gemini 看圖生成觀察與初稿。
6. 由 Codex 依本 SOP 校稿。
7. 產出 review JSON / Markdown，等待使用者確認。
8. 使用者明確同意後，才寫回 PostgreSQL。

## Gemini 使用規則

此任務的照片判讀全部交給 Gemini。Codex 不應只看標題憑空補文案。

每篇建議提供 Gemini：

- `id`
- `title`
- `category`
- `heroImage`
- 5-8 張代表照片，優先使用封面、近景、全景、主舞台、拍照區、產品或文字可辨識照片
- 同品牌或同主題兄弟篇 ID / title，如果已知

Gemini 必須輸出：

- `observedText`：照片裡可辨識的文字、品牌、年份、場地
- `visualElements`：可確認的視覺元素，例如花藝、背板、道具、色系、舞台、展台
- `serviceIntent`：可推論的服務重點，但不能寫成已確認事實
- `buyerSearchTerms`：可能對應的搜尋詞
- `draftDescription`：初稿
- `confidence`：high / medium / low
- `needsHumanCheck`：需人工確認的品牌名、場地名、年份或人物資訊

禁止 Gemini 或後續校稿擅自補：

- 照片和標題都沒有出現的客戶全名
- 不確定的場地
- 不確定的年份
- 不確定的人名、明星名、IP 名稱
- 價格、報價、優惠、保證效果

## 文案結構

預設每篇 220-280 中文字。若使用者要求更完整 SEO，可放寬到 280-380 字，但需避免重複灌關鍵字。

標準結構：

第一段：情境破題

- 40-80 字。
- 用現場瞬間切入。
- 讓讀者快速知道這是哪一類活動或空間。
- 例句模式：「賓客一進場，先被 XXX 吸引，這就是 XXX 佈置最重要的瞬間。」

第二段：設計方法與 SEO 場景

- 120-170 字。
- 明確寫村山良作做了什麼。
- 放入 3-5 個自然關鍵字。
- 說明適用的 B2B 場景。

第三段：CTA

- 30-60 字。
- 要面向活動主辦、品牌端、HR、行銷、代理商或公部門承辦，不面向一般消費者。
- 建議預設句型：

```text
想為下一場企業春酒、尾牙或品牌活動打造有記憶點的主題場景？立即透過村花囍 LINE 預約檔期，詢問村山良作的客製佈置方案。
```

若頁面不適合硬 CTA，可改成較自然收尾：

```text
當活動畫面能被拍下、被分享、被記住，品牌想傳達的故事就會從現場延伸到更多人眼前。
```

但只要使用者明確說「也要 CTA」，就使用前者或其同義句。

## SEO / AEO 關鍵字池

依相簿內容自然選用，不要每篇全塞。

通用：

- 活動佈置
- 會場佈置
- 主題場景設計
- 拍照牆設計
- 打卡牆設計
- 商業空間佈置
- 客製化佈置

企業 / 商業：

- 品牌活動佈置
- 企業活動佈置
- 春酒佈置
- 尾牙佈置
- 新品發表會
- 品牌記者會
- 快閃活動佈置
- 展區佈置

婚禮 / 公部門：

- 婚禮佈置
- 聯合婚禮
- 戶政拍照區
- 戶政結婚牆
- 公部門空間美化

AEO 寫法要直接回答潛在問題：

- 這個案例適合誰？
- 現場做了哪些區塊？
- 它解決了什麼活動問題？
- 為什麼這樣做有助於拍照、分享或品牌識別？
- 如果我也有類似活動，能怎麼延伸？

## 校稿規則

完成 Gemini 初稿後，Codex 必須校稿：

- 改成繁體中文。
- 刪除 bullet list、hashtag、emoji、括號式硬塞關鍵字。
- 避免「我們最專業」、「完美呈現」、「頂級」、「全台第一」等誇大句。
- 確認每篇至少有 3 個自然 SEO 關鍵字。
- 確認至少一次出現「村山良作」。
- 確認 CTA 包含明確行動，例如 LINE 預約、預約檔期。
- 確認沒有提到價格、報價、優惠。
- 確認沒有把推測資訊寫成事實。
- 確認換行格式適合後台 description 欄位，通常段落間用一個空行。

## Review 檔格式

補文案任務預設先輸出 review 檔，不直接寫回資料庫。

建議檔名：

```text
docs/seo-aeo-copy/album-descriptions-empty-review-YYYYMMDD.json
```

欄位：

```json
{
  "generatedAt": "YYYY-MM-DD",
  "source": "正式站 API 或 PostgreSQL snapshot",
  "scope": "description 為空的作品",
  "styleReference": "docs/seo-aeo-copy/album-descriptions-20260505.json",
  "items": [
    {
      "id": "...",
      "title": "...",
      "category": "...",
      "oldDescription": "",
      "newDescription": "...",
      "cta": "...",
      "seoTerms": ["活動佈置", "品牌活動佈置"],
      "geminiObserved": ["照片可確認元素"],
      "needsHumanCheck": [],
      "confidence": "high",
      "notes": ""
    }
  ]
}
```

## 寫回資料庫規則

只有在使用者明確說「確認」、「可以寫入」、「上線」、「套用到正式站」等語意時，才執行寫回。

寫回前必須：

- 備份 PostgreSQL 或至少匯出受影響文章的 `id/title/description/updated_at`。
- 再次確認只更新 `description` 為空的條目，除非使用者明確要求覆蓋既有文案。
- 保留 review 檔與寫入清單。
- 寫入後抽查 `/works/{id}` 的 meta description、頁面內文與 JSON-LD description。

## 完成回報格式

回報時只講重點：

- 篩出幾篇空白描述。
- 產出哪個 review 檔。
- 文案是否都含 CTA。
- 有哪些低信心或需人工確認的品牌/場地/年份。
- 是否尚未寫入正式資料庫。

範例：

```text
已依補充空白描述 SOP 產出 12 篇 review 文案，檔案在 docs/seo-aeo-copy/album-descriptions-empty-review-20260508.json。全部都有 SEO/AEO 結構與 B2B CTA，尚未寫入 PostgreSQL。低信心項目有 2 篇，主要是不確定照片中的場地名稱，需要你確認後再上線。
```
