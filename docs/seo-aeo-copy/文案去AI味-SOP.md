# 作品文案去 AI 味 SOP

本文件定義「清除既有文案 AI 寫作痕跡」類任務的標準流程。之後只要提到「去 AI 味」、「humanizer」、「文案檢查」、「文案讀起來像 AI」、「清掉 AI 腔」等近似用詞，就依本文件處理。

與 `補充空白描述-SOP.md` 的差別：那份處理「沒有文案」，本份處理「有文案但寫得像 AI」。

## 任務目標

檢查正式站作品的 `description`，找出並改寫帶有 AI 生成痕跡的文案，同時**不得損失 SEO 關鍵字、不得捏造事實、不得破壞 CTA**。

## 資料源與格式鐵律

- 正式資料源是 PostgreSQL `goodjob_site.articles`，**不是** `data/articles.json`（那是舊備份）。
- `description` 存**純文字**：空行（`\n\n`）分段，**嚴禁 HTML 標籤**（前端走 `textContent` + CSS `pre-wrap`，放 `<p>` 會原樣顯示成文字）。
- 換行必須是 **LF**，不可 CRLF。
- SSR `/works/{id}` 的 `<meta name="description">`、`og:description`、JSON-LD `description` **全部取自 description 的前 157 字**（`server.py:2436`）。
  → **第一段就是 Google 搜尋結果的 snippet**，AI 味最該優先清的就是第一段。

## 五道關卡（缺一不可）

### 關卡 1：定位（關鍵字掃描）

用誇大詞／宣傳詞／否定式排比／殘留符號打分，快速找出重災區。

**但關鍵字掃描有天生盲區**：抓得到「頂級／奢華／星光熠熠」這種誇大詞，**抓不到「沒有誇大詞但通篇空洞宣傳腔」的文案**。

> 2026-07-14 踩坑：`d579ef80`（安樂戶政）關鍵字掃描 **0 分**，內文卻是「打卡聖地」「成功弱化」「大幅提升」「化身為精緻的攝影棚」通篇自誇。單靠關鍵字會直接放行。

### 關卡 2：語感複審（不可省略）

**掃描分數低的篇章一定要用 LLM 逐篇讀過**，判準不是「有沒有踩到某個詞」，而是：

> **這段有沒有點名真實的東西？**
> 乾淨的文案寫得出實物與設計決策（花材色階、低反射面料、「避免過度熱鬧」）；
> 壞文案只宣告效果（「成功打造」「大幅提升」「展現質感與用心」），讀完不知道現場長什麼樣。

### 關卡 3：改寫

- **風格錨點用該篇自己已經寫得好的段落**，不要用外部範本。舊文案常是「AI 味前段 + 後補的乾淨後段」拼接，後段就是目標語氣。
- 硬性保留：CTA 逐字、至少一次「村山良作」、原有 SEO 關鍵字、原文的實物與品牌事實。
- 220–400 字（原文常有 466–598 字，改寫後短三成是正常的）。

### 關卡 4：事實稽核（最容易被跳過，也最危險）

**改寫 agent 會捏造事實。** 這是實測結果，不是假設。

> 2026-07-14 踩坑：18 條原文沒有的新增宣稱被寫進改寫稿——`7369ddb5` 憑空生出「新人在戶政待不到一小時」、豪鼎三篇擅自把場地寫成「飯店大廳」、`d579ef80` 寫出「情人湖吊橋是基隆人約會會走的一段路」、`92387fe2` 把**跨案場的方案選單**誤寫成「這場尾牙做了 A+B+C」的單場事實。

檢查方向要**雙向**：

| 方向 | 抓什麼 | 工具 |
|---|---|---|
| 舊有 → 新無 | SEO 關鍵字流失 | 腳本（子字串比對） |
| **新有 → 舊無** | **捏造事實** | 腳本粗篩（英文／數字／引號）**＋ LLM 判讀**（中文的描述性斷言腳本抓不到） |

紅線（SOP 明文禁止）：照片與標題都沒出現的客戶全名、不確定的場地、不確定的年份、人名／IP 名、價格。
合法來源：該篇 `title`、該篇 `oldDescription`。**不可跨篇借用姊妹篇的事實。**

### 關卡 5：驗收（不可自驗）

**agent 的自我驗證不可信。**

> 2026-07-14 踩坑：改寫 agent 宣稱「SEO 關鍵字流失 0」，獨立重跑實測**掉了 2 個**。另一個 agent 修掉了原文的「段落重複」，卻**自己把 CTA 貼了兩次**（它掛在自檢那一步之前）。

獨立腳本必查：AI 痕跡分數、SEO 關鍵字流失、**跨篇近似重複**、篇內段落重複、簡體字、HTML 標籤、CRLF、CTA 逐字、字數。

重大交付（≥3 篇寫入）**派 fresh-context agent 驗收**，不自驗。

## 跨篇重複（duplicate content）

站上文案曾有 7 組「方法論模板」被 2–3 篇一字不差共用，佔各篇內文 23–33%。

**偵測要用相似度，不能用逐字比對。**

> 2026-07-14 踩坑：`6031ac6a` 與 `d65a02f9` 的模板段相似度 **96.5%**（只差開頭「不只是漂亮，而是讓」vs「要讓」，是事實校正時去掉否定式排比造成的），逐字比對直接判定「不重複」而放行。改用 `difflib.SequenceMatcher`，門檻 70%。

處理原則：**保留論點骨架與 SEO 關鍵字，但每篇換說法、換切入角度、用該篇自己的素材舉例。**

註：**結尾 CTA 跨篇重複是正常的**（行銷用語本該一致，Google 不會為 CTA 扣分），不要把它當 duplicate content 去重。

## 寫回資料庫

只有使用者明確說「確認 / 可以寫入 / 上線 / 套用到正式站」才寫。

四步儀式：

1. **備份全表**（不只要改的那幾篇）：`id / title / description / updated_at / sort_order`，另存每篇 description 的 hash。
2. **寫入**：SQL 用 `$GJ$...$GJ$` dollar-quoting 包 description（保護換行與引號）、`BEGIN/COMMIT` 交易包裹。
   **Windows 傳中文鐵律**：SQL 檔 → UTF-8 base64 → SSH 只傳 ASCII → 遠端 `base64 -d`。**禁** here-string／stdin／pipe 直傳中文。傳完比對 md5。
3. **讀回驗證**：改的篇章逐字相符；**沒改的篇章 hash 必須一字未變**（證明沒誤觸鄰列）。
4. **獨立交叉驗證**：`curl` live 站 `/works/{id}`，確認 `<meta name="description">`、JSON-LD `description`、頁面內文 `<p class="works-desc">` 三個輸出點都更新，且舊 AI 詞在線上 0 命中。
   `updated_at` 是好用的獨立證人——**時間戳有變動的列數必須恰好等於預期篇數**。
