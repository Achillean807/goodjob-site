# 村山良作 部署護欄與災難復原 runbook

更新日期：2026-05-06
背景：歷史上 3 次部署誤覆蓋 PostgreSQL（相簿 / 文案被清空）。本份 runbook
記錄事後加上的多層護欄、為什麼這樣設計、以及災難真的發生時怎麼還原。

## 一、災難根因（過去 3 次推測）

| 嫌犯 | 機制 |
|---|---|
| 1. `data/articles.json` 被 git 追蹤 | `scp -r *` / 主機端 `git pull` 把 master 上過時的 JSON 蓋過主機 runtime 副本 |
| 2. PostgreSQL 環境變數失效時靜默 fallback SQLite | systemd override `postgres.conf` 失效 / 忘了 `daemon-reload` → `_using_postgres()` 偵測為 False → 走 SQLite 路徑 |
| 3. SQLite 為空時自動從 JSON seed | `_init_db` 看到 `COUNT == 0` → `_replace_articles` 把過時 JSON 灌進去 → 線上資料被舊版重置 |
| 4. `--migrate-runtime-to-postgres` 沒保護 | 任何手滑跑此 flag → `DELETE FROM articles` → 灌過時 JSON → 線上資料蒸發 |

## 二、目前已加的護欄（程式 + 設定）

### 護欄 A — `data/articles.json` 從 git untrack
- `git rm --cached data/articles.json data/wp_texts.json`
- `.gitignore` 加上這兩個檔
- 效果：repo 不再有舊副本可被 `git pull` / `scp -r` 散播
- 風險殘留：如果有人用 `scp -r * /srv/.../`，本機 working tree 的 `data/articles.json` 還是會被帶上去
- 補救：部署一律用 `git archive` + `tar -xf`（見 `docs/村山良作-部署資訊清單.md`）

### 護欄 B — 預設禁止 SQLite fallback（fail-fast）
位置：`server.py` `main()` 開頭
```text
若 GOODJOB_DATABASE_URL 沒設 且 GOODJOB_ALLOW_SQLITE != 1
→ stderr 印 fatal 訊息 → exit 1
```
效果：
- systemd override 失效時，service 起不來（journalctl + Cloudflare 立即發現）
- 不會偷偷退到 SQLite 路徑

### 護欄 C — SQLite 從 JSON seed 預設禁用
位置：`server.py` `_init_db()` SQLite 分支
```text
若 GOODJOB_ALLOW_JSON_SEED != 1
→ 跳過從 articles.json / accounts.json / config.json 自動 seed 的步驟
```
效果：
- 萬一 B 護欄被繞過走到 SQLite 路徑，也不會把 JSON 資料覆蓋上去
- migrate flag 路徑會自動 enable 此旗標，不影響合法用途

### 護欄 D — `--migrate-runtime-to-postgres` 加 `--force-replace`
位置：`server.py` `main()` migrate flag 分支 + `_pg_count_articles()` helper
```text
target PostgreSQL 已有 articles 且 --force-replace 沒帶
→ stderr 印 fatal → exit 1
```
psycopg2 沒裝會 raise RuntimeError（不會被 swallowed），避免「環境壞掉」被誤判成「target 是空」。

## 三、本機開發 / 主機 prod 應該怎麼設

### 主機 prod（`/srv/weddingwish/goodjob-sit/`）
systemd override `/etc/systemd/system/murayama-goodjob.service.d/postgres.conf`：
```ini
[Service]
Environment="GOODJOB_DATABASE_URL=dbname=goodjob_site user=achilean"
```
**不要**設 `GOODJOB_ALLOW_SQLITE`，**不要**設 `GOODJOB_ALLOW_JSON_SEED`。
任何一個錯誤組合都會被護欄擋下。

### 本機 dev
PowerShell 範例：
```powershell
$env:GOODJOB_ALLOW_SQLITE = "1"        # 准許 SQLite
$env:GOODJOB_ALLOW_JSON_SEED = "1"     # 准許首次從 articles.json seed
python server.py --port 8000
```
或用 `--migrate-runtime-to-postgres ...` 時兩個 flag 都會自動開啟，無需手設。

## 五、災難真的發生：如何還原

### 還原前的證據蒐集（5 分鐘）
```bash
ssh achilean@100.102.51.64
# 1. 先把當前異常狀態凍結
pg_dump goodjob_site > /tmp/incident_$(date +%Y%m%d_%H%M%S).sql
# 2. 看相關 log
sudo journalctl -u murayama-goodjob.service --since '1 hour ago' | tail -100
# 3. 確認 systemd env 是否正常
systemctl show murayama-goodjob.service -p Environment
```

### 從備份還原 PostgreSQL
```bash
# 主機端
sudo systemctl stop murayama-goodjob.service
# 找最近的健康備份
ls -lt /srv/weddingwish/goodjob-sit/data/goodjob_site*.sql | head
# 也可從本機備份回拉
# scp D:/AI_Code/goodjob-site/backups/<timestamp>/goodjob_site.sql achilean@host:/tmp/restore.sql

# 還原
psql -d postgres -c "DROP DATABASE goodjob_site;"
psql -d postgres -c "CREATE DATABASE goodjob_site OWNER achilean;"
psql -d goodjob_site < /srv/weddingwish/goodjob-sit/data/goodjob_site.pre_fix_<timestamp>.sql

# 驗證
psql -d goodjob_site -Atc "SELECT count(*) FROM articles;"
psql -d goodjob_site -Atc "SELECT count(*) FROM article_images;"

# 重啟服務
sudo systemctl start murayama-goodjob.service
sudo journalctl -u murayama-goodjob.service -n 30 --no-pager
# 看到 'DB backend  : PostgreSQL' 才算正常
```

### 還原 R2 圖片（如果有遺失）
R2 預設不會自己被刪。圖片消失通常是 `articles` / `article_images` 表的 URL 不見，但 R2 物件還在。先比對 R2 listing 與 PG：
```bash
/home/achilean/bin/rclone ls r2:goodjob-images > /tmp/r2.txt
# 對照本機 backups/<timestamp>/r2-listing.txt
diff /tmp/r2.txt <(sort backups/<timestamp>/r2-listing.txt | sort)
```
若 R2 真有缺檔（極罕見），用 `migrate_to_r2.py --article <slug>` 從本機原檔重灌。

## 六、定期備份

主機上 `host-gdrive-backup.timer` 已經把 PostgreSQL 納入每日 Google Drive 備份鏈路。
重大變更前手動再做一次：
```bash
ssh achilean@100.102.51.64 "pg_dump goodjob_site > /srv/weddingwish/goodjob-sit/data/goodjob_site.pre_change_$(date +%Y%m%d_%H%M%S).sql"
```

## 七、護欄驗證 checklist

部署 server.py 變更後，主機端跑這份：
```bash
# 1. service 應該正常起來
sudo systemctl status murayama-goodjob.service
sudo journalctl -u murayama-goodjob.service -n 10 --no-pager
# log 必須出現 'DB backend  : PostgreSQL'

# 2. 故意把 PG env 拿掉，service 應該起不來
sudo systemctl stop murayama-goodjob.service
sudo -u achilean env -u GOODJOB_DATABASE_URL python3 /srv/weddingwish/goodjob-sit/server.py --port 39999
# 必須印 [fatal] GOODJOB_DATABASE_URL is not set 並 exit 1
sudo systemctl start murayama-goodjob.service

# 3. 線上驗證
curl -s https://goodjob.weddingwishlove.com/api/articles | python3 -c 'import json,sys; d=json.load(sys.stdin); print(len(d.get("articles",[])))'
# 數字應該 ≥ 49
```
